# 状态和类型的设计

## 一、 数据伴随状态 vs 数据与状态分离

在 Rust 中设计状态和类型时，有一个非常经典的权衡问题：**“数据伴随状态” vs “数据与状态分离”**。

在设计 ConnectionState 时，可以用在状态的 enum 变体中包含该状态下所需的数据字段，例如：

```rust
enum State<const N: usize> {
    Connecting(Option<oneshot::Sender<io::Result<()>>>),
    Connected {
        recv_buf: ReceiveBuffer<N>,
        send_buf: SendBuffer<N>, 
        sent_packets: SentPackets,
        closing: Option<Closing>,
    },
    Closed {
        err: Option<Error>,
    },
}

pub struct Connection<const N: usize> {
     state: ConnectionState<N>,
     ...
}
```

也可以，用一个不包含数据的 enum 作为状态，把需要的数据全部都放在 Connection 对象中，例如：

```rust
enum ConnectionState {
    Connecting,
    Connected,
    Closed,
}

pub struct Connection<const N: usize> {
    state: ConnectionState,
    notification: Option<oneshot::Sender<io::Result<()>>>,
    recv_buf: ReceiveBuffer<N>,
    send_buf: SendBuffer<N>, 
    sent_packets: SentPackets,
    closing: Option<Closing>,
    close_err: Option<Error>,
    ...
}
```

下面为你详细剖析两种方式的优缺点，并给出针对 uTP 库的最佳实践建议。

---

### 方式一：数据伴随状态

数据包含在 Enum 变体中，这种方式遵循 Rust 的核心理念：**Make invalid state unrepresentable（让非法状态不可表示）**。

#### 优点
1. **绝对的类型安全**：在 `Connecting` 状态下，你根本无法访问 `recv_buf`，因为编译器不允许。这杜绝了“在未连接时误读缓冲区”的低级错误。
2. **内存效率高**：Enum 变体共享同一块内存空间（大小取决于最大变体 + 判别式）。而方式二中，所有字段同时存在，如果为了安全加上 `Option`，会带来大量的内存碎片和体积膨胀。
3. **语义清晰**：状态和数据强绑定，代码的阅读者一眼就能看出哪个状态拥有哪些数据。

#### 缺点
1. **模式匹配的冗长**：每次要操作 `recv_buf` 时，都需要 `if let State::Connected { recv_buf, .. } = state`，写起来啰嗦。
2. **借用检查的痛点**：这是最头疼的。如果你需要同时修改 `State` 内部的 `recv_buf` 和 `State` 外部的某个字段，Rust 的借用规则会让你很难解构 `State`。

#### 优化方案（最佳实践）

为了克服缺点，**不要把所有字段直接平铺在 Enum 里，而是将它们提取成独立的结构体**：

```rust
// 1. 提取 Connected 状态的数据到独立结构体
pub struct ConnectedData<const N: usize> {
    recv_buf: ReceiveBuffer<N>,
    send_buf: SendBuffer<N>,
    sent_packets: SentPackets,
    closing: Option<Closing>,
}

// 2. 状态机定义
enum State<const N: usize> {
    Connecting(Option<oneshot::Sender<io::Result<()>>>),
    Connected(ConnectedData<N>),
    Closed { err: Option<Error> },
}

// 3. 在 Connection 中实现辅助方法，缓解借用检查和模式匹配的痛点
impl<const N: usize> Connection<N> {
    /// 获取 Connected 状态的可变引用，如果不是 Connected 则返回错误
    fn as_connected_mut(&mut self) -> io::Result<&mut ConnectedData<N>> {
        match &mut self.state {
            State::Connected(data) => Ok(data),
            State::Closed { err } => Err(err.take().unwrap_or_else(|| io::Error::new(io::ErrorKind::NotConnected, "Connection closed"))),
            State::Connecting(_) => Err(io::Error::new(io::ErrorKind::ConnectionPending, "Connection is still connecting")),
        }
    }

    // 这样在处理 uTP 报文时，就可以很方便地操作了：
    fn on_data_packet(&mut self, pkt: DataPacket) -> io::Result<()> {
        let connected = self.as_connected_mut()?; // 一行搞定解构和校验
        connected.recv_buf.insert(pkt);
        // 如果还需要操作 Connection 的其他非 state 字段，这里也不会有借用冲突
        Ok(())
    }
}
```

### 方式二：状态与数据分离

#### 优点
1. **写起来像 OOP 语言（如 Java/C++）**：直接 `self.recv_buf` 访问，不需要模式匹配。
2. **容易同时借用多个字段**：你可以同时可变借用 `self.state` 和 `self.recv_buf`，不存在解构 `self` 导致的借用冲突。

#### 缺点（致命）
1. **非法状态可以表示**：当 `State::Connecting` 时，`recv_buf` 是什么状态？它必须被初始化！这意味着你要么提供一个空的 `ReceiveBuffer::new()`（可能引发无意义的内存分配），要么把所有字段改成 `Option`（变成 `Option<ReceiveBuffer<N>>`）。
2. **运行时 Panic 风险**：如果改成 `Option`，你在收到数据包时必须写 `self.recv_buf.as_mut().unwrap()`。一旦逻辑出错，在 `Connecting` 状态收到了 Data 包，程序直接 Panic。uTP 这种网络库最忌讳 Panic。
3. **状态与数据的一致性靠人脑维护**：你必须手动保证“当 State 变成 Closed 时，要把 send_buf 清空”。一旦忘记，就会出现状态是 Closed，但缓冲区里还有数据的灵异事件。

---

### 针对 uTP 库的特殊考量

uTP 是基于 UDP 的可靠传输协议，状态机会非常频繁地在 `Connecting` 和 `Connected` 之间转换，且 `Connected` 状态下会有极其复杂的逻辑（拥塞控制、ACK 确认、重传定时器等）。

1. **状态的原子切换**：
   当握手成功，从 `Connecting` 切换到 `Connected` 时，方式一非常优雅：
   ```rust
   // 方式一：数据伴随状态，状态切换时数据自然就位
   let sender = match std::mem::replace(&mut self.state, State::Closed { err: None }) {
       State::Connecting(s) => s,
       _ => unreachable!(),
   };
   self.state = State::Connected(ConnectedData {
       recv_buf: ReceiveBuffer::new(),
       send_buf: SendBuffer::new(),
       // ...
   });
   sender.map(|s| s.send(Ok(())));
   ```
   如果是方式二，你需要手动初始化或清理一堆散落在 `Connection` 各处的字段，极易遗漏。

2. **内存布局**：
   uTP 的 `ReceiveBuffer` 和 `SendBuffer` 通常是环形缓冲区，如果 `N` 比较大（比如 64KB 或 128KB），在方式二中，即使处于 `Connecting` 状态（尚未传输数据），也必须分配这么大的内存，这对高并发连接是非常浪费的。方式一只有在进入 `Connected` 状态时才会分配这些缓冲区。

## 二、 enum 对齐造成的内存浪费

Enum 的大小等于其最大变体的大小加上判别式，这会造成内存浪费（内部碎片）。

比如在设计 Packet 时，可以用简约的 enum 作为类型：

```rust
pub enum PacketType {
    Data,
    Fin,
    State,
    Reset,
    Syn,
}

pub struct Packet {
    seq_nr: u16,
    ack_nr: u16,
    pack_type: PacketType,
    payload: Vec<u8>,
    ...
}
```

也可以使用带数据的 enum 作为类型：

```rust
pub enum PacketType {
    Data {payload: Vec<u8>, selective_mask: Vec<[bool; 32]>},
    Fin {payload: Vec<u8>, selective_mask: Vec<[bool; 32]>},
    State {selective_mask: Vec<[bool; 32]>},
    Reset,
    Syn,
}

pub struct Packet {
    conn_id: u16,
    seq_nr: u16,
    ack_nr: u16,
    pack_type: PacketType,
    payload: Vec<u8>,
    ...
}
```

先说结论：**带数据的 enum 作为类型的 Packet 由于内存对齐，会造成大量的内存浪费，强烈建议不要使用！**

但是为什么之前 ConnectionState 的设计中使用带数据的 enum 作为状态，同样会有对齐的内存浪费，而我们却推荐这种设计呢？

这背后是 Rust 系统编程中关于**栈空间、堆空间、对象生命周期和类型安全**的深度权衡。让我们详细拆解：

### 1. 核心区别：单个长期对象 vs 海量短期对象

**Packet（网络数据包）的特点：**
- **海量**：每秒可能有成千上万个包在收发。
- **短命**：解析完、处理完就丢弃。
- **结构悬殊**：SYN 包只有 Header（几十字节），Data 包有 Header + Payload（可能几百到几千字节）。
如果用 Enum 承载，由于对齐，每个 SYN 包都会占用 Data 包的大小，这在高频分配下是**灾难性**的内存浪费。

**ConnectionState（连接状态）的特点：**
- **唯一**：一个连接只有**一个**状态机实例。
- **长期**：存活于整个连接的生命周期（几分钟甚至几小时）。
- 既然每个连接始终只有 1 个 State 实例，那么 Enum 因为对齐而多出的那点内存，影响微乎其微。

### 2. 关键机制：缓冲区在堆上，不在栈上

这是最关键的一点。让我们看看 `ConnectedData` 的内存布局：

```rust
pub struct ConnectedData<const N: usize> {
    recv_buf: ReceiveBuffer<N>,
    send_buf: SendBuffer<N>, 
    sent_packets: SentPackets,
    closing: Option<Closing>,
}
```

在 uTP 这种网络库中，`ReceiveBuffer` 和 `SendBuffer` 为了性能，通常会使用固定大小的环形缓冲区。但**这个固定大小 `N` 的底层数组，一定是分配在堆上的**（比如使用 `Box<[u8; N]>` 或者 `Vec<u8>` 预分配）。

因此，`ConnectedData` 结构体本身在**栈上**占用的内存其实很小，仅仅是一堆指针、长度、索引和一些状态标记（可能就 100~200 字节）。

我们来看看 Enum 的内存分配情况：

```rust
enum State<const N: usize> {
    Connecting(Option<oneshot::Sender<io::Result<()>>>), // 占用约 8-16 字节
    Connected(ConnectedData<N>),                         // 占用约 100-200 字节（指针等）
    Closed { err: Option<Error> },                       // 占用约 20-30 字节
}
```

当状态处于 `Connecting` 时，Enum 确实会因为对齐而占用 `Connected` 变体那么大的**栈空间**（约 200 字节）。
**但在网络编程中，为了几百字节的栈空间去妥协类型安全，是极其不划算的。** 栈空间非常便宜，这点对齐浪费完全可以忽略不计。

### 3. 对比“分离设计”的内存真相

如果我们为了不浪费这 200 字节的栈空间，采用你之前提到的“方式二（数据分离）”，会发生什么？

```rust
pub struct Connection<const N: usize> {
    state: State, // 枚举很小
    recv_buf: ReceiveBuffer<N>, // 始终存在
    send_buf: SendBuffer<N>,   // 始终存在
    // ...
}
```

- 当连接处于 `Connecting` 状态时，虽然 `State` Enum 很小，但是 `recv_buf` 和 `send_buf` 必须作为 `Connection` 的字段存在！
- 如果它们的内部数据不是 `Option` 包裹的堆分配，那么它们在 `Connection` 创建时就必须分配好堆内存（连接还没建立，就白白了占用了几百 KB 的缓冲区内存）。
- 如果它们是 `Option<ReceiveBuffer<N>>`，虽然可以在 `Connecting` 时为 `None`，但你每次访问都要 `unwrap()`，回到了之前说的运行时 Panic 风险，而且 `Option` 本身也增加了结构的复杂度。

**结论**：采用 Enum 方式，在 `Connecting` 阶段，我们仅仅浪费了约 200 字节的**栈空间**，但**零堆内存分配**。这比分离设计白白分配几十 KB 堆内存要好得多！

### 4. 终极逃生舱：如果栈对齐真的成了问题怎么办？

如果你的 `ConnectedData` 设计得非常奇葩，里面包含了巨大的栈数组（比如 `ConnectedData { raw_data: [u8; 8192] }`），导致 Enum 的对齐浪费不可接受，Rust 提供了一个完美的解决方案：**将最大变体装箱（Box）**。

```rust
enum State<const N: usize> {
    Connecting(Option<oneshot::Sender<io::Result<()>>>),
    // 将巨大的 ConnectedData 放到堆上，栈上只保留一个胖指针 (8 bytes)
    Connected(Box<ConnectedData<N>>), 
    Closed { err: Option<Error> },
}
```

通过 `Box`：
1. `Connected` 变体在栈上只占 8 字节（指针）。
2. Enum 的整体大小被彻底压缩，不再有严重的栈对齐浪费。
3. 状态切换时，只需要交接堆上的指针，拷贝成本极低。
4. **类型安全丝毫不受影响！** 依然享受编译器的穷举检查和状态绑定。

## 总结

1. **Payload 是海量、短命且大小悬殊的纯数据**：用 Enum 会导致灾难性的内存/缓存浪费，且缺乏解析上下文，所以用扁平的 Struct + Header 区分。
2. **State 是单一、长期、强调逻辑互斥的状态机**：用 Enum 虽然会因对齐浪费少量栈内存，但换来了 Rust 最强大的类型安全和零成本抽象。如果最大状态真的很大，用 `Box` 包装即可完美解决。在设计 uTP 库这种底层基础设施时，**逻辑的正确性和状态的一致性，永远高于几十字节栈空间的优化。**
